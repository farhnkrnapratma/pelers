## Git workflow

This repo uses **git-flow-next** (classic preset — https://git-flow.sh/). The config is committed in `.gitflow`; on a fresh clone run `git flow config sync` to activate it (and create `develop` with `git branch develop origin/develop` if it is missing locally), then `bash .githooks/install.sh` to install the git hooks (`bun install` does the hooks and the commitlint tooling through the `prepare` script).

- `main` — release only. Never commit directly; only `release/*` and `hotfix/*` branches merge into it (and get tagged).
- `develop` — integration branch. `feature/*` and `bugfix/*` branch from and merge back into it.
- `feature/<name>`, `bugfix/<name>` — parent `develop`. `git-flow feature start <name>` / `git-flow feature finish <name>`.
- `release/<name>`, `hotfix/<name>` — parent `main`, started from `develop`/`main` respectively, merge into `main`, tagged on finish.

**Always sign off commits** (`git commit -s ...`, including on `git-flow` `feature`/`release`/`hotfix` finish operations).

Commit messages must follow [Conventional Commits](https://www.conventionalcommits.org), enforced by commitlint (`commitlint.config.js`) in the `commit-msg` hook and in CI; validate a candidate message with `printf '%s' "<message>" | bunx commitlint`.

CI runs on CircleCI (`.circleci/config.yml`): `reuse lint`, format/lint, tests, `cargo deny`, secret scan (trufflehog) and commitlint on every push.

## Rust port

The Rust core in `src/` is being ported from the TypeScript renderer in `ts/`, and the package exposes only a JS/TS binding (napi, later WASM). `ts/` is the oracle: a diagram type's TypeScript is deleted only after the Rust output is byte-identical on the golden corpus and a differential fuzz run is clean. SVG parity needs JS number semantics (`Math.round` ties go toward +infinity, UTF-16 text widths, insertion-ordered maps, stable sorts); do not use `f64::round` or hash-map iteration order in rendering code. The reference SVGs live in `tests/golden/` (generated by `bun scripts/gen-golden.mjs` after `bun run build` in `ts/`; regenerate only when the oracle changes); a type joins `tests/golden/parity.txt` once `cargo test --test golden` matches every case, and from then on that test must stay green. The `info` diagram prints the package version, so `ts/package.json` and `Cargo.toml` must carry the same version; after a bump, rebuild `ts/dist` and regenerate the goldens. Text and SVG-builder behaviour is also checked against `tests/fixtures/text.json` (`bun scripts/gen-fixtures.mjs`, compared by `tests/text_oracle.rs`); YAML, preprocessing, entity encoding and error-offset mapping against `tests/fixtures/preprocess.json` (`bun scripts/gen-fixtures-preprocess.mjs`, compared by `tests/preprocess_oracle.rs`). Write no comments in code. Run the oracle's commands from `ts/` (`bun run typecheck`, `lint`, `fmt:check`, `test`) and the core's from the repo root (`cargo test`, `bun run test:native`).

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
