## Git workflow

This repo uses **git-flow-next** (classic preset — https://git-flow.sh/). The config is committed in `.gitflow`; on a fresh clone run `git flow config sync` to activate it (and create `develop` with `git branch develop origin/develop` if it is missing locally), then `bash .githooks/install.sh` to install the git hooks (`bun install` does the hooks and the commitlint tooling through the `prepare` script).

- `main` — release only. Never commit directly; only `release/*` and `hotfix/*` branches merge into it (and get tagged).
- `develop` — integration branch. `feature/*` and `bugfix/*` branch from and merge back into it.
- `feature/<name>`, `bugfix/<name>` — parent `develop`. `git-flow feature start <name>` / `git-flow feature finish <name>`.
- `release/<name>`, `hotfix/<name>` — parent `main`, started from `develop`/`main` respectively, merge into `main`, tagged on finish.

**Always sign off commits** (`git commit -s ...`, including on `git-flow` `feature`/`release`/`hotfix` finish operations).

Commit messages must follow [Conventional Commits](https://www.conventionalcommits.org), enforced by commitlint (`commitlint.config.js`) in the `commit-msg` hook and in CI; validate a candidate message with `printf '%s' "<message>" | bunx commitlint`.

CI runs on CircleCI (`.circleci/config.yml`): `reuse lint`, format/lint, tests, `cargo deny`, secret scan (trufflehog) and commitlint on every push.

## Rust port

The Rust core in `src/` is a port of Pele 1.13.0, and the package exposes only a JS/TS binding (napi and WASM). The oracle is Pele's own source in a sibling checkout, `../pele` at tag 1.13.0 (override with `PELE_DIR`); the fixture and golden generators import it through `scripts/oracle.mjs`, and the benchmarks use the official npm releases of `pele` and `mermaid` (`bench/package.json`). Every name pelers emits or accepts uses `pelers` (`pelers-*` classes, `--pelers-*` variables, `Pelers`); never write `pele-` names into this repository. `scripts/oracle.mjs` is the only place that maps between the two: `toUpstream` renames inputs before they reach Pele, `normalize`/`writeFixture` rename its output, and the documented exceptions are applied there (the `info` diagram measures `Pelers v<Cargo version>`, sankey gradient ids hash the `pelers` stops, cynefin renders with `idPrefix: "pelers"`). The xychart tick rounding (`toPrecision(15)`) is a deliberate fix over Pele. SVG parity needs JS number semantics (`Math.round` ties go toward +infinity, UTF-16 text widths, insertion-ordered maps, stable sorts); do not use `f64::round` or hash-map iteration order in rendering code. The reference SVGs live in `tests/golden/` (generated by `bun scripts/gen-golden.mjs`, which also pins `todayMarker off` on time-of-day gantt charts; regenerate only when the oracle or the version changes); a type joins `tests/golden/parity.txt` once `cargo test golden` matches every case, and from then on that test must stay green. Text and SVG-builder behaviour is also checked against `tests/fixtures/text.json` (`bun scripts/gen-fixtures.mjs`, compared by `src/tests/text_oracle.rs`); YAML, preprocessing, entity encoding and error-offset mapping against `tests/fixtures/preprocess.json` (`bun scripts/gen-fixtures-preprocess.mjs`, compared by `src/tests/preprocess_oracle.rs`); whole-diagram renders and series palettes against `tests/fixtures/render-<type>.json` (`bun scripts/gen-fixtures-render.mjs`, compared by `src/tests/render_oracle.rs`) and `tests/fixtures/palette.json` (`bun scripts/gen-fixtures-palette.mjs`, compared by `src/tests/palette_oracle.rs`); add a fixture generator branch and a test per type that joins `parity.txt`. The oracle and golden tests live in `src/tests/` (compiled only under `cfg(test)`) so that one test binary covers the core; keep them there, because `cargo llvm-cov` counts a line as covered only when a single binary executes it. Coverage target is zero uncovered lines and functions (`cargo llvm-cov --locked --summary-only`). Write no comments in code. Run the core's commands from the repo root (`cargo test`, `bun run test:native`).

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:

- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
